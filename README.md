# cc-manifest-lab

CC_Codex 二期（26.11）**数据工程**产品线：**湖区落地清单台**（Litestar + Preact CDN + SQLite）。

## 一句话骨架（自有，非外仓抄题）

**湖区落地批次 → 对象指纹登记 → 清单闭合 → 可见性对账**

与现有七线正交（不是采集目录、ETL 管道、同步源、解析入库、编排流、种子摄取、留存裁撤）。
不碰外仓常见指纹（Feed 归并 / CDC 游标 / 质检签发 / Slicegate 类仓名）。

## 领域

- **所属领域**：数据工程
- **子方向**：数仓与数据湖（落地清单 / 对象登记闭环）

## 技术栈

| 层 | 选型 |
|----|------|
| 后端 | Python 3.12、Litestar、Uvicorn、SQLite |
| 前端 | 原生 JS SPA（全中文，侧栏），靛青竖纹 + 亮青强调；不依赖外网 CDN |
| 测试 | pytest + httpx（本地秒级闭环，优先于 compose） |

## 基线已通主链

1. 湖区落地批次列表（收集中 / 已闭合）
2. 向批次登记对象键与内容指纹
3. 闭合清单（对象数固化，拒绝空批）
4. 可见性对账报告（闭合批 vs 开放批 vs 孤儿对象）

## 跨区依赖门禁与处置（bug-11）

种子数据故意留出缺口：**订单银区已闭合，其上游订单铜区仍在收集**，解析链路在依赖门禁提前掐断。

| 概念 | 说明 |
|------|------|
| 依赖卡片 | 银区 ← 铜区，展示银区闭环、铜区进度、依赖是否对齐 |
| 依赖门禁 | 银区闭合须等铜区齐套；拧了就拦（`409 上游铜区未齐套，禁止闭合`） |
| 处置 | 二选一，一次事务只落一边，失败返回短句 |
| 整笔回滚 `rollback` | 银区恢复收集中、对象退回已登记、闭合记录作废，铜区继续收集 |
| 隔离放行 `quarantine` | 隔离铜区缺口、写本机隔离凭证，银区保持已闭合放行 |
| 芯片 | `待处置` / `回滚` / `隔离` / `已对齐` |
| 本机库存证 | 每次成功处置生成 `VCH-日期-依赖-版本-随机` 凭证，可回看 |

互斥与并发：处置用 `BEGIN IMMEDIATE` 单写事务 + 下游 `version` 乐观校验；
两名编排员同点，只有一笔落库，另一笔得到 `409 依赖已处置` 或 `409 依赖已变化`。

四处同查：依赖卡片、批次详情（银区详情 / 铜区进度）、解析编排台、可见性对账
（依赖缺口计入 `mismatch_count`）使用同一份依赖状态，芯片与凭证必须一致。

**只改依赖卡片颜色、不改处置写入 = 仍失败**：芯片由落库后的处置记录派生，不靠前端推断。

预留切口（未做，供后续功能题）：清单换版生效窗、批量失败闭互斥、清单回灌等。
